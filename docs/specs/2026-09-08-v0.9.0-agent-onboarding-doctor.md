# PortMarshal v0.9.0 — Agent Onboarding and Doctor

> Baseline: 2026-09-08, v0.8.1 (`27700d9`). This is the original v0.9.0 design contract.
> Local test results, validation limitations and the 2026-09-20 release follow-up are recorded in `docs/acceptance/2026-09-08-v0.9.0.md`.

## Outcome

An agent can follow a short, host-specific guide to start a development service with the existing
ownership guard, then use `portmarshal doctor` to explain installation, identity, state, and service
problems. A user can distinguish an actual problem from a diagnostic that lacks enough evidence.

The two required deliverables are maintained Codex / Claude Code / Cursor templates and a read-only
doctor command. Success means a documented start → inspect → logs → guarded stop workflow works in an
isolated project, including a second session being blocked from changing the first session's service.

## Baseline findings

| Current evidence | Consequence for v0.9.0 |
| --- | --- |
| `src/owner.ts` resolves explicit `PORTMARSHAL_OWNER`, then Codex thread/session IDs | Keep this identity precedence; explain when only project-level ownership is available |
| Only `integrations/claude-code` ships a dedicated guide/skill | Add Codex and Cursor adapters with the same lifecycle and safety policy |
| The Claude skill omits detached startup and recommends plain `gc` during diagnosis | Add `run -d`, readiness and logs; use `gc --dry-run` for cleanup previews; correct exit-code-3 guidance |
| `Registry.load()` repairs modes, migrates legacy state, and renames invalid JSON | Doctor needs a separate observation path, not a call to `load()` or another CLI command |
| `realExec` discards errors and returns stdout | Empty scan output alone cannot establish that no listeners exist |
| The scanner conditionally queries Docker and PM2 | Doctor must control these probes rather than assume that invoking a runtime client has no side effects |
| `buildServiceSnapshot` already aggregates listeners and claims | Reuse its grouping and stale-claim policy when inputs support a conclusion |
| `package.json` publishes only `dist`, `README.md`, and `LICENSE` | Include the reviewed integration assets in the release package and verify the packed contents |

## Scope

Required for 0.9.0:

- `doctor [--project DIR] [--json]`: runtime, scanner, project, registry, owner, and service findings.
- Stable diagnostic IDs, explicit observation limits, bounded execution, and a separate versioned JSON report.
- Codex skill and `AGENTS.md` snippet; updated Claude Code skill and `CLAUDE.md` snippet; Cursor project rule.
- Integration index, troubleshooting guide, bilingual README updates, and isolated acceptance coverage.

Deferred: `init` / automatic rule installation, `doctor --fix`, ownership transfer or adoption commands,
stop previews, audit history, heartbeats, auto-restart, a resident daemon, MCP, Windows support, and a GUI.
SwiftBar executable/version mismatch checks are useful follow-up work, not a 0.9.0 release requirement.
The existing SwiftBar troubleshooting documentation stays available.

## Agent integration contract

Use a shared policy described in `integrations/README.md`, with short self-contained host adapters.
Do not introduce a template generator for three adapters. Each adapter must cover:

1. Check the installed version and run `doctor --project .`; explain warnings before starting a service.
2. Use `run -d` when the agent must continue after startup, or foreground `run` when supervision is intended.
   Use `{port}` for frameworks that ignore `PORT`; include a `/health` readiness example.
3. Inspect using `list --services --project . --json`, `whois <port> --json`, and `logs <name>`.
4. Preserve one owner identity throughout the session. A new owner per command breaks ownership continuity;
   one constant owner shared by all sessions defeats session isolation.
5. Exit code 3 can mean a live instance, an owner mismatch, or insufficient ownership evidence. Inspect the
   reason; do not blindly retry with `--restart`, generate a new identity, or add `--force`.
6. Use guarded `stop`; `release` releases a claim without stopping a process. Use `gc --dry-run` to preview
   cleanup. Do not use raw process signals or mutating cleanup as an automatic conflict workaround.

| Host | Planned artifact and installation target | Identity behavior |
| --- | --- | --- |
| Codex | `integrations/codex/skills/portmarshal/SKILL.md` → project `.agents/skills/portmarshal/SKILL.md`; guide includes an appendable `AGENTS.md` snippet | Preserve explicit owner when present; otherwise let the existing resolver recognize Codex IDs |
| Claude Code | Existing skill → project `.claude/skills/portmarshal/SKILL.md`; guide includes a `CLAUDE.md` snippet | Preserve explicit owner. A documented skill session substitution is a candidate bridge only after host verification |
| Cursor | `integrations/cursor/rules/portmarshal.mdc` → `.cursor/rules/portmarshal.mdc`, with a focused description and `alwaysApply: true` | Preserve explicit owner; otherwise explain project-level fallback unless the host supplies a verified stable identity |

Guides must explain how to merge with existing instructions without overwriting them. Manual project-level
installation is the default; optional user-level instructions may be documented separately. Installing a
rule does not prove that a particular invocation loaded it: record a fresh host-session acceptance result.

`PORTMARSHAL_OWNER` remains the portable contract. Do not add guessed Claude/Cursor environment variables
to `resolveOwnerIdentity`. Claude's `${CLAUDE_SESSION_ID}` is documented as skill-content substitution;
this alone does not prove that a shell environment variable exists. If the bridge is verified, pass the
resolved value consistently to each command using proper shell quoting, never by relying on a previous
tool call's `export`. Otherwise ship the explicit-owner/project-level fallback guide and label that limit.

Doctor reports the owner source and whether an identity is available. It cannot prove that the value is
unique across sessions, that future commands will retain it, or that every unregistered listener has a
session owner. Another session's healthy service is informational, not an error.

## Doctor CLI contract

```text
portmarshal doctor
portmarshal doctor --project .
portmarshal doctor --project /path/to/project --json
```

Default service scope is the current canonical project directory and its descendants. `--project` selects
another existing directory; invalid or missing values fail before probing. Do not accept positional targets,
child commands, mutation flags, or `--show-sensitive-command`. Validate doctor arguments without changing
the parsing behavior of existing commands.

Collect the machine-wide observable listener set before project filtering. Otherwise a reused port in
another project could be misreported as an unlistened claim. Report findings only for the selected project,
plus the minimum conflicting-port evidence needed to explain them. Do not read project instruction files,
run package scripts, bind a test port, or send HTTP requests to user services.

### Findings and severity

| Stable check ID | Expected behavior |
| --- | --- |
| `runtime.platform` | macOS/Linux pass; unsupported platform is an error and dependent probes are skipped |
| `runtime.node` | Check against the installed package's engine requirement; avoid a network lookup |
| `runtime.installation` | Show the currently running package version, CLI real path and Node path; do not claim it is the latest version or execute other PATH candidates |
| `project.directory` | Resolve and canonicalize the requested directory; inaccessible or invalid paths are errors |
| `scanner.listeners` | Missing required command, denied access, or timeout is an error; valid empty output is distinct from failed execution |
| `scanner.attribution` | Missing PID/cwd/ancestry evidence is a warning; show coverage limits rather than inventing an owner |
| `scanner.managed-metadata` | Runtime enrichment omitted by doctor is explicitly skipped; affected service conclusions are partial |
| `state.registry` | Missing state on first use is healthy; unreadable, invalid, or oversized state is an error, never an empty registry |
| `state.permissions` | Observed mode/ownership issues warn; missing state is skipped; never change modes or try a write |
| `state.legacy` | Legacy-only registry is a warning about migration pending; do not migrate it or infer current claims from it |
| `state.concurrent-change` | Changing registry or lock observation makes ownership conclusions incomplete; never acquire or reclaim a lock |
| `owner.identity` | Identified source passes; missing identity warns that new claims use project-level fallback |
| `services.review` | Stale claim, drift, unknown ownership, and a confirmed dead managed run warn; a corroborated active detached service does not |
| `services.conflict` | A confirmed contradictory claim or shared-port project conflict is an error; unrelated healthy sessions are not conflicts |

The report uses check statuses `pass`, `warn`, `error`, `skipped`. Overall status is the highest finding
severity; skipped checks do not themselves count as warnings. When a skipped or failed observation limits
a required conclusion, emit a corresponding warning/error and set `complete: false`.

Exit codes for doctor: `0` for pass or warnings, `1` for errors or invalid usage. Warnings remain visible in
JSON and text; scripts needing a clean report inspect `status`. Do not repurpose existing exit codes 2–4.
These exit codes describe this diagnostic run, not permission to stop or release a service.

### JSON and output

Doctor gets its own `schemaVersion: 1`; `list --services --json` remains unchanged. The report is:

```ts
interface DoctorReport {
  schemaVersion: 1;
  version: string;
  project: string | null;
  status: "pass" | "warn" | "error";
  complete: boolean;
  owner: { source: "explicit" | "codex" | "none"; available: boolean };
  checks: Array<{
    id: string;
    status: "pass" | "warn" | "error" | "skipped";
    summary: string;
    details: string[];
    nextSteps: string[];
  }>;
}
```

Use deterministic check ordering. Details are bounded, sanitized explanations, not raw probe output.
Text and JSON derive from the same report. Valid `--json` invocations always produce one JSON object on
stdout, including expected probe failures; parse/usage errors may retain the existing stderr convention.
Do not interleave progress text into JSON. Unexpected failures must not dump raw child-process errors.

Never include raw environment values, session IDs, owner fingerprints, run markers, logs, raw registry
contents, or process command lines in doctor output. Project/executable paths and relevant ports/PIDs may
be shown for local diagnosis; this is not an anonymized support bundle. Sanitize control characters in
file-derived labels and summaries. Next steps are suggestions only and must not default to forced stop,
claim release, permission repair, or mutating `gc`.

## Observation implementation boundaries

### State

Add a dedicated inspector (proposed `src/diagnostics/registry.ts`) using the same state-directory selection
as `Registry`, but never calling `load()`, `withLock()`, or mutation helpers. Inspect existing metadata and
read at most 4 MiB of `registry.json`; reject an over-limit file without partial parsing. Validate the array,
required entry fields and known optional field types; accept unknown additive fields for compatibility.
Invalid timestamps/ports must not feed stale-claim or service inference.

Compare file identity/size/mtime before and after reading; permit one bounded retry for concurrent changes.
Observe an existing lock and mark the snapshot provisional. Do not wait for lock expiry or conclude that a
lock is abandoned from age alone. Avoid following a non-regular registry file; report it for review. Keep
legacy state, backups, permissions and contents unchanged, including during malformed-file handling.

### Scanner

Introduce an injected diagnostic executor / observation hook around existing scanner parsing. Keep the
normal `realExec` and existing CLI defaults compatible. Record command outcome categories (success,
recognized no-match, missing, denied, timeout, truncated, failed) before stdout is parsed. In particular,
`lsof` no-match handling must use command-specific evidence and must not turn arbitrary nonzero exits into
successful empty scans. Linux socket rows without visible PIDs require an explicit coverage warning.

Use bounded `execFile` calls, not a shell: per-probe timeout at most 3 seconds, an overall collection budget
of 10 seconds, and output bounds no larger than the existing 16 MiB. Cancel outstanding probes at the
deadline and emit an incomplete report. Preserve batching; no per-PID external commands or repeat full scans.
Linux proc-file observation failures also need coverage reporting, not just command exit reporting.

Doctor does not invoke Docker or PM2 clients in this version. Add an opt-out scanner option with legacy
defaults preserved. List visible managed listeners as observed, mark metadata unavailable, and suppress
claim/project conclusions that would rely on container/application metadata. Do not interpret the Docker
backend's cwd as the service project or claim that a managed service has been fully diagnosed.

### Services

Reuse `buildServiceSnapshot` and `isStaleClaim` on validated inputs. Doctor must suppress unsupported
negative conclusions: incomplete listener coverage cannot establish that a claim is stale; denied process
visibility cannot establish a dead run; missing managed metadata cannot establish a foreign project.
Use a tri-state liveness observation for doctor (`alive`, `gone`, `unknown`); a permission error is unknown.
Provide injection points where existing boolean liveness helpers would otherwise discard this distinction.

Snapshot output is an observation, not a stop authorization. Existing `stop` identity revalidation,
owner hashing, claim adoption, stale age threshold, and registry mutation semantics remain unchanged.

## Acceptance and release gates

1. Fresh home/state: doctor does not create directories, migrate legacy data, or create a registry/lock.
2. Invalid/unreadable/oversized registry: structured error; no chmod, backup rename, truncation or replacement.
3. Concurrent registry writes and a present lock: bounded, incomplete observation without cleanup or repair.
4. Missing/denied/timed-out/truncated scanner, valid no-match, and Linux PID-less sockets: distinct results;
   no false all-clear, stale-claim, dead-run, or foreign-project conclusion.
5. Temporary project with healthy managed/unmanaged fixtures, stale claim, drift and conflict: correct
   severity; a corroborated detached service stays healthy; exactly 30 minutes remains non-stale.
6. Two identities in the same project: existing claim/release/stop/restart guard still blocks the second
   owner; doctor merely explains its observed identity and ownership findings.
7. Privacy sentinels in environment, registry, commands and probe errors: absent from text/JSON; fake
   Docker/PM2 clients are never executed by doctor. Doctor never sends terminating signals to existing services; deadline
   cancellation may terminate only diagnostic child processes it started itself.
8. All three adapters document the same lifecycle, conflict handling and owner continuity. Record actual
   host versions, invocation/loading evidence and fallback limitations; fixture-only checks do not prove
   host integration. The optional Claude identity bridge ships only if separately verified.
9. Full build, tests and real-listener smoke pass on Ubuntu/macOS × Node 22/24. Confirm the engine floor
   remains compatible, or propose that change explicitly rather than silently raising it.
10. Inspect the packed npm files for all three integration assets; verify README commands and links against
    the packaged CLI. Add the 0.9.0 changelog and version bump only when the implementation is ready.

Tests use temporary state, projects and listeners; they do not operate on the user's live registry or services.
Release execution remains a separate authorized step: local checks → main CI → tag → npm OIDC/provenance
verification → GitHub Release. Planning does not initiate any of these remote mutations.

# PortMarshal v0.8.0 — Service-level Ownership

## Goal

Represent a local development service as a verified or inferred unit containing its listener processes,
wrapper ancestry, process group, ports, cooperative claims, project, and safe stop strategy. A detached
listener is an attachment state, not automatically an error.

## Service identity

The aggregator groups listeners in this order:

1. PortMarshal `run -d` identity (`runId` plus PGID, with the process marker re-verified before signalling)
2. Docker container ID or PM2 application ID
3. Canonical project path plus PGID
4. A single listener PID fallback

Project path alone is never sufficient to merge two live services. This protects repositories that run
multiple independent front-end, API, worker, or test services.

Linux `ss` parsing must retain every visible PID for a shared socket. macOS `lsof` already emits one
listener record per PID. Scanner work remains bounded to a fixed number of system commands; no per-PID
`ps` or environment scan may be added.

## State model

Each service exposes independent dimensions:

- activity: `active`, `reserved`, or `dead` for a managed run whose recorded process is gone
- attachment: `attached`, `detached`, `managed`, or `none` for claim-only services
- confidence: `verified`, `corroborated`, `inferred`, `unknown`, or `conflict`
- claim relation: `current`, `reserved`, `related`, `drift`, or `conflict`

An active detached service with a canonical project and matching claim is corroborated and is not counted
as an error. Detached origin markers remain informational and never authorize a destructive action.

## Claim relations

A claim on a listening port is `current`. A non-listening claim may be attached as `related` only when the
project has exactly one live service or a stronger owner/service identity matches. If multiple live services
exist in the project, the claim remains its own reserved service. `superseded` is intentionally omitted from
automatic inference: different service names in the same project may both be legitimate.

Existing per-port merge states and `list --json` remain compatible. The new service JSON shape is exposed
through `list --services --json` with `schemaVersion: 1`.

## Safety

- Docker, PM2, and verified `run -d` services keep their delegated/group stop behavior.
- Inferred unmanaged process groups are grouped for display but never gain automatic group-kill authority.
- `stop <port>` keeps the existing guarded behavior and re-scans immediately before signalling.
- Agent-session owner conflicts remain blocked unless the existing explicit force/GUI review path is used.
- Menubar cleanup remains review-only; no menu action invokes `gc --kill-detached`.

## User-facing behavior

- `list --services` renders one row per service, with all ports and listener/wrapper PIDs.
- `whois <port>` includes an additive `Service` section while preserving the existing primary listener data.
- `watch` tracks service IDs when service view is enabled.
- SwiftBar renders one top-level row per service, with listener/wrapper/claim details in submenus.
- The menu footer shows the running PortMarshal version and executable path.

## Acceptance case: alab_frontend

Given npm wrapper PID 37909 and Vite listener PID 37929 in PGID 37907, active port 3000, and a separate
non-listening claim on 5173:

- one active service is rendered for port 3000;
- wrapper and listener PIDs are both visible;
- detached origin `claude-code` is informational and does not increase the error count when ownership is
  corroborated;
- claim 5173 appears as a related reserved claim requiring review;
- no claim is released and no process group is signalled automatically.

## Release gates

- parser fixtures for multiple PIDs sharing one port on Linux and macOS;
- service grouping tests for one PID/many ports, many PIDs/one port, wrapper/listener ancestry, same project
  with different PGIDs, managed runtimes, claims, conflicts, and owner sessions;
- JSON compatibility tests and command-redaction/privacy tests;
- build, full test, and smoke on Ubuntu/macOS with Node.js 22 and 24;
- real macOS npm/Vite menubar and `whois` acceptance without touching unrelated services.

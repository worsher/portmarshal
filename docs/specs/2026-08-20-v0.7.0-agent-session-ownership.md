# PortMarshal v0.7.0: Agent-session ownership

## Problem

PortMarshal v0.6.x protects services by live project attribution and cooperative claims. That prevents one project from stopping another project's service, but two coding-agent sessions operating in the same checkout still share the same trust boundary. A second session can currently reuse a reserved claim, release it, or use `run --restart`/`stop` against the first session's claimed service.

## Goals

- Bind cooperative `claim` and `run` records to an agent-session identity when one is available.
- Block a different session from reusing, releasing, restarting, or stopping that claimed service by default.
- Never persist the raw session identifier.
- Preserve compatibility with v0.6.x registries and ordinary terminals that expose no stable session identity.
- Keep `--force` as an explicit, review-first human override for `release` and `stop`.

## Identity contract

PortMarshal derives an owner identity in this order:

1. `PORTMARSHAL_OWNER`, an explicit portable identity supplied by an integration or shell.
2. `CODEX_THREAD_ID`, then `CODEX_SESSION_ID`, when running inside Codex.
3. No session identity. Existing project-level behavior remains in effect.

The selected value is hashed with SHA-256 together with its source. Only a versioned, truncated fingerprint (`v1:<hex>`) and a non-sensitive source label are written to `registry.json`; the raw value is never stored or printed. The same `PORTMARSHAL_OWNER` value intentionally permits a controlled handoff between processes.

## Registry behavior

- New identified claims store `ownerKey` alongside the existing `claimedBy` label.
- Repeating a claim with the same owner remains idempotent.
- Reusing an active owner-bound `(project, name)` claim from a different or unidentified session exits with code 3 and does not mutate the record.
- A legacy active claim without `ownerKey` is adopted by the first identified caller that safely reuses it.
- `release` checks the owner fingerprint. `release --force` is the explicit recovery/takeover path.
- Releasing or garbage-collecting a record clears `ownerKey`, minimizing long-lived linkable metadata; a subsequent claim stores only its new caller's fingerprint.

## Stop and restart guard

When a live listener belongs to the caller's project but an active claim on one of its ports has another `ownerKey`, classification returns `session` rather than `own`. `stop` and therefore `run --restart` exit 3 without signaling the process. The diagnostic says that another agent session owns the claim and names only its non-sensitive `claimedBy` label.

`stop --force` keeps its existing semantics: after the caller reviews attribution, it may override both project and session guards. On macOS, `--gui` remains the interactive confirmation alternative. Managed Docker, PM2, and `run -d` identity checks remain unchanged.

## Compatibility and limits

- v0.6.x registry entries have no `ownerKey` and continue to use project ownership until adopted.
- Unregistered listeners cannot be tied to a session reliably, so they retain project-level classification.
- Environments without a stable automatic identifier can opt in with `PORTMARSHAL_OWNER`.
- This is cooperative ownership, not an OS security boundary. A process with access to the user's state directory can edit the registry or use `--force`.

## Acceptance

- Raw owner values never appear in persisted state or command output.
- Same-owner claim/release/stop flows keep working.
- Cross-owner claim, release, stop, and `run --restart` are blocked with exit code 3.
- Legacy ownerless records remain usable and can be adopted without migration commands.
- Build, unit tests, smoke tests, package dry-run, and `git diff --check` pass on the supported toolchain.

# PortMarshal v0.6.1 safety hardening

> 2026-08-04. This patch release tightens the existing safety contract; it does not add a supervisor, a service manifest, or new service-manager integrations.

## Goals

1. Redact sensitive command-line values before process data reaches CLI renderers or JSON output. A deliberate `--show-sensitive-command` escape hatch is available for local debugging.
2. Keep `~/.portmarshal`, its registry, lock metadata, and detached-run logs private to the current user.
3. Never let a stale cooperative claim override contradictory live project attribution.
4. Treat detached or otherwise unattributed listeners as guarded targets unless live project attribution proves that they belong to the caller.
5. Bind `run -d` lifecycle actions to a random run identity and the spawned process group. Readiness must be served by that run, and `stop` must not signal a process group whose identity no longer matches the registry.

## Command redaction

`scanListeners` still uses the raw command internally for project inference, then stores a redacted form in `ProcessInfo.command`. Redaction covers common token, secret, password, authorization, cookie, and API-key flag/assignment forms, bearer credentials, URL userinfo, and sensitive query parameters.

`--show-sensitive-command` disables this output-boundary redaction. Help and documentation must warn that its output can contain credentials and should not be pasted into issues or agent transcripts.

## Private state

- state and log directories: `0700`
- registry, lock pid, current logs, and rotated logs: `0600`

Every access repairs the mode of an existing state directory/registry so upgrades secure previously created data. Log setup similarly repairs existing log paths.

## Guarded stop semantics

Live project attribution wins over registry history:

- same project (including existing parent/child project matching): `own`
- known different project: `foreign`, even if the port has a caller-owned claim
- unknown project with a caller-owned claim: `own` cooperative fallback
- detached/unknown without corroborating project or claim: guarded (`detached`), requiring `--force`

For `run -d`, registry entries store `runPid` plus a random `runId`. The child receives `PORTMARSHAL_RUN_ID` and descendants inherit it. Group termination requires the listener PGID to match `runPid` and its environment marker to match `runId`. Legacy v0.6.0 entries without `runId` may use the existing service-name marker plus matching PGID/project as a compatibility fallback.

## Readiness ownership

TCP/HTTP readiness alone is insufficient because another process could bind the probed port between claim and child bind. After an endpoint responds, `run -d` scans the listener and verifies both:

- listener PGID equals the spawned group id;
- listener `PORTMARSHAL_RUN_ID` equals the current random run id.

An ownership mismatch is reported as a distinct readiness failure, then the spawned group is cleaned up and the claim is released.

## Out of scope

- systemd/launchd-native stop delegation
- log size/time retention
- `doctor`, JSONL watch, or a versioned agent protocol
- multi-service manifests
- Windows support
